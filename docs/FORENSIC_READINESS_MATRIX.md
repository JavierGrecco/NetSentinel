# Matriz de preparación pericial de NetSentinel Forense

**Estado de esta rama:** laboratorio experimental. Esta matriz distingue una función que existe y tiene pruebas de una garantía forense que todavía no se puede afirmar. No es certificación, acreditación ni asesoramiento legal.

## Referencias de trabajo

- [SWGDE 18-F-002-2.0 — Best Practices for Digital Evidence Collection (30 de junio de 2025)](https://www.swgde.org/documents/published-complete-listing/18-f-002-2-0/): seguridad, integridad durante el ciclo de vida, inventario, registro contemporáneo y transferencias de custodia.
- [SWGDE 17-F-002-2.1 — Best Practices for Computer Forensic Acquisition](https://www.swgde.org/documents/published-complete-listing/17-f-002-2-1/): identificación del elemento, herramienta y versión, hashes, adquisición, errores y transferencia con remitente, receptor, fecha/hora y propósito.
- [SWGDE 18-Q-002 — Requirements for Report Writing in Digital and Multimedia Forensics](https://www.swgde.org/documents/published-complete-listing/18-q-002-swgde-requirements-for-report-writing-in-digital-and-multimedia-forensics/): informe, solicitud, alcance, materiales, procesos/resultados, disposición y autorización del informe.
- [NIST SP 800-86 — Guide to Integrating Forensic Techniques into Incident Response](https://csrc.nist.gov/pubs/sp/800/86/final): orientación técnica para integrar técnicas forenses en respuesta a incidentes; no sustituye procedimientos jurídicos u organizacionales.

## Matriz de estado y criterio para considerar cada control completo

| Área que espera revisar un especialista | Estado en esta rama | Qué se puede afirmar | Qué falta para afirmar preparación profesional |
|---|---|---|---|
| Identificación de caso, autorización y alcance | Implementado; pruebas automatizadas | La apertura exige identificador, referencia de autoridad, objetivo, alcance, examinador y un nombre de operador declarado. | Vincular la autorización real, su vigencia y las limitaciones aprobadas; identidad de usuario aún no autenticada. |
| Inventario y recepción | Implementado con salvedad de migración | El formulario distingue quién entrega y quién recibe/quién queda a cargo al ingreso; guarda hora declarada con offset y zona horaria declarada aparte. El custodio receptor es el punto de partida para las transferencias consecutivas. | Reconciliar los registros antiguos cuyo destinatario no quedó documentado (la migración deja el campo vacío y las transferencias se bloquean); completar organización, identificadores del dispositivo/medio, condición/embalaje al ingreso y validar el procedimiento con el organismo responsable. |
| Transferencias de custodia | Implementado en esta rama; requiere CI y prueba manual | Cada transferencia registra remitente, receptor, fecha/hora declarada con offset, motivo, método, estado opcional del embalaje y precinto opcional. Se agrega como evento inmutable y encadenado; los manifiestos lo incluyen. Se rechaza una discontinuidad con el último custodio declarado, una auditoría rota y un caso cerrado. | Completar y revisar todos los traslados reales, recepción inicial, devoluciones y disposición final; auditar el flujo con personal que aplique el procedimiento institucional. Los nombres siguen siendo declarados. |
| Hash y verificación de copia | Parcial, SHA-256 | La comparación opera solo sobre un nombre dentro de la carpeta protegida de copias de trabajo; registra coincidencia, discrepancia o error. | Las prácticas de adquisición pueden requerir más de un algoritmo, por ejemplo SHA-256 y SHA-512, más hashes de adquisición/verificación calculados en los momentos correctos. Aquí no se adquieren imágenes ni se compara una adquisición en streaming. |
| Auditoría encadenada | Implementado con límites | Las filas son de solo anexado desde la aplicación/base y cada evento enlaza un digest SHA-256 con el anterior. La consulta identifica filas faltantes o modificadas; no repara la cadena. | Anclaje externo independiente (por ejemplo firma con clave fuera del equipo, timestamp confiable o repositorio inmutable), gestión de claves, control de acceso y validación ante un administrador con acceso a la base. El usuario local con control del equipo puede modificar una base completa fuera de la aplicación. |
| Manifiestos exportables | Implementados; pruebas automatizadas | Se exportan manifiesto de auditoría y expediente JSON con hashes internos verificables; incluyen la cadena de transferencia y metadatos sin contenido binario ni rutas completas. | Anclar la huella exportada en otro canal, versionar informes firmados y probar interoperabilidad/retención conforme a la política de la organización. Un digest interno no autentica el origen. |
| Herramientas, método y reproducibilidad | Parcial | Las verificaciones registran versión de NetSentinel, hora, tamaño, hashes y resultado. | Registro estructurado del software externo usado, versión/build, método/procedimiento, parámetros, archivos de salida, errores de adquisición, excepciones y pasos que otra persona pueda repetir. |
| Informe de examen | No implementado como informe formal | El expediente consolida inventario, checks y auditoría; no produce una conclusión pericial. | Informe autorizado con título, solicitante, propósito, material examinado, método y resultados, artefactos de apoyo, conclusiones con base observable, desviaciones, disposición de originales/derivados, firma/autorización y control de enmiendas. |
| Autenticación, roles y separación de tareas | No implementado | El operador escribe su nombre para documentar cada acción. | Identidad autenticada, roles, permisos mínimos, sesiones protegidas, separación de quien registra/aprueba, revisión independiente y, cuando corresponda, firma individual de actos. No presentar el texto de actor como identidad verificada. |
| Custodia/retención del material | Parcial, fuera del alcance de almacenamiento integral | NetSentinel conserva metadatos y calcula hashes de copias locales designadas; no copia ni almacena la evidencia original. | Un repositorio de evidencia controlado, permisos y retención, copias verificadas, respaldo, controles de acceso, exportación segura y procedimientos de conservación/disposición. No añadir un recolector universal improvisado. |
| Pruebas y calidad | Parcial; laboratorio sintético | La suite automatizada comprueba flujos API/UI, eventos encadenados, rechazos, exportaciones y casos sintéticos. | Terminar CI de la cabeza final; luego realizar una revisión visual/funcional controlada, revisión de seguridad independiente y pruebas con datasets de referencia aprobados, hashes conocidos y criterios de aceptación documentados. No usar evidencia real para la primera validación. |

## Bloqueantes antes de cualquier uso como registro oficial

1. **CI de la cabeza final completamente verde**, incluidas las pruebas Chromium de la transferencia y ambos manifiestos.
2. **Prueba de aceptación con datos sintéticos** en el mismo árbol/versión que se propone desplegar; registrar resultado, entorno, versión y limitaciones.
3. **Revisión independiente de seguridad y procedimiento** sobre autenticación, permisos, firma/ anclaje externo y manejo físico del material.
4. **Definir el alcance**: esta rama no adquiere discos, no demuestra una cadena de custodia legal por sí sola y no sustituye a herramientas forenses especializadas ni procedimientos institucionales.

## Decisión de producto recomendada

Mantener esta rama como laboratorio de validación y no presentarla como una suite forense lista para evidencia real. La próxima fase con mayor valor es la recepción explícita por custodio, el informe reproducible y el anclaje externo verificable; autenticación/roles y retención protegida se deben diseñar antes de habilitar un flujo multiusuario.
